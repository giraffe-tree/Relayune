# 核心测试链路与执行顺序

**功能分类与 App 点击步骤：**[核心 case 操作手册](core-case-operation-guide.md)。先按功能选范围，再按本页约定执行与记录。

对应[核心测试树](core-user-journeys.md)与[可执行叶子](core-user-journey-cases.md)。2026-09-09 按用户要求改为共享前置、沿真实使用链路执行；使用优先级保持递进 80% 定义。

## 共享一次准备，结果仍逐项判断

复用已经独立授权的 Web / 原生手机和本轮专用项目，先确认版本、登录、网络、设备占用。创建会话 S/T，各自使用不同随机标记、草稿、图片和输出路径。每条测试开始前确认其前置真实成立；前一步失败时，只有依赖该状态的后续动作受阻，其余分支继续。

同一次动作可以支持多个断言，但不能因为整条链路“走完了”就把所有叶子打勾。操作仅计时一次，通过 evidence ID 关联多个场景，场景耗时不得直接相加；同时保留第一次失败和恢复尝试。

## 供应商顺序

用户指定顺序时优先遵循；未指定时默认 Codex → Claude Code → Kimi Code → Pi，其他已冻结 Agent 接续执行。每家内部按下表串联旅程，不逐个叶子重复创建前置。跨 Agent 隔离等用例保留必要的双 Agent 夹具，并在依赖就绪后闭环；不得因单家主线走完就把跨 Agent 参数判为通过。共享环境预检可以集中完成，真实能力探针按供应商推进，避免同时发起多个模型轮次增加状态管理成本。

## 建议顺序

| 顺序 / 链路 | 连续动作 | 可共同覆盖的场景 | 独立保留的断言 |
| --- | --- | --- | --- |
| 0 · 环境 | 确认已安装版本、账户、Agent、独立授权和设备占用 | CORE-002-01 手输分支可引用刚完成的真实配对证据 | 初次登录、扫码不能由已有登录或手输通过代替 |
| 1 · 项目与首轮 | 选父目录 → 新项目空态 → 创建 T → 新建 S（手机默认名称） → S 首轮与追问 | CORE-006-01、005-02、007-01、008-01/02；顺带核对 005-01 | 目录实际落盘；S 空历史；T 不变；真实回复与终态；追问不含答案 |
| 2 · 切换与草稿 | S/T 分别记住不同标记 → 各留草稿 → 切换往返 → 分别只追问自己的标记 → 换项目/Agent | CORE-010-01 各参数、012-01 纯文字/文字加图片 | 两边分别校验；图片不混入；同 Agent 不能替代跨 Agent |
| 3 · 结果与阅读 | 同会话输出列表/代码/表格 → 附图识别 → 图片/工具预览 → 翻历史 → 旧位置收到新回复 → 返回最新 | CORE-012-02、017-01/02/03/04、018-01 | 长回复不是超过一页消息历史；预览关闭后锚点；旧锚点保持与重新跟随分别判断 |
| 4 · 决定与控制 | S/T 独立任务/审批 → S 批准、T 保留 → 另路径拒绝 → 结构化问题与答案草稿 → 运行中补充/队列 → 停止 S、T 继续 → S 再发 | CORE-010-02、011-01、013-01/02/04/05、014-01/02/04/05、015-01/02、008-04、016-01/04、019-01 | 固定人工审批模式；批准精确内容/拒绝文件不存在；先确认真实能力；子任务必须有两个独立结果 |
| 5 · 恢复与离线 | 完成多轮后刷新 Web/重开手机 → 追问标记 → 客户端单独断网 → 恢复补齐 → Desktop 离线 → 启动后追问 | CORE-022-01 各参数、021-01/02/04 | 先结束受控任务；不得用关闭浏览器代替断网；不得用客户端断网冒充 Desktop 离线 |
| 6 · 系统与首次状态 | 手机前台事件抑制 → 离开会话后真实通知与点击；隔离实例首次登录/扫码 | CORE-020-01/02、001-01、002-01 扫码 | 真机要求按原用例保留；不为了“已测”退出共享 Desktop 账户或复制凭据 |

每个目标 Agent 的“决定与控制”链路必须分别执行电脑发起、手机新建两种来源下的手机审批与手机回答（CORE-013-04/05、CORE-014-04/05，均为固定 P0）。手机新建可复用项目与授权，但不得复用电脑创建的会话冒充手机新建；完成后检查原轮过程中的终态及重开恢复。

每个目标 Agent 控制链路另必测 CORE-015-04/05 与 CORE-016-05/06：电脑发起/手机新建 × 手机终止/手机直接发消息中断后继续。运行中发送须验证旧轮终态先于新轮启动，不以普通 steering 代替。

登录/配对仅在待测场景要求时重新执行；每个新客户端必须取得新的独立授权码，在有效期内核对实际输入后立即提交。断网、停止 Desktop、退出登录安排在正常路径之后，且不能影响其他任务的资源占用。

## 通用运行约束

- 每轮从当前测试树冻结范围；历史报告的行数不作为新一轮范围。2026-09-09 的 36 行仅属于当日剩余链路（内部验收档案未随公开源码提供）。
- Web 优先 Chrome，使用当前待测供应商的真实 Agent；手机在取得 QA 专用设备 lease 后再执行。已安装版本与源码 HEAD 分别记录，纯测试不重建或部署。
- 等待上限与分阶段诊断统一按[提速流程](core-regression-efficiency.md)执行，不给连续轮询重复延长截止时间。计时包含工具观察开销，单次样本不称 P95 或纯渲染性能。
- 没执行的核心动作记 `not-run`；有证据说明前置无法满足才记 `blocked`；已执行但断言失败记 `failed`。支持某能力的限定组合可通过，其他参数仍需单列，不能拿一个平台代表所有平台。

## 历史故障形成的通用约束

先在准备项目和夹具时检查 Relay PID、存活与 RSS，再执行正常主线；每条链路切换时复查。若 Relay 退出，保存脱敏崩溃类型和时间，暂停依赖在线的分支，不用反复重启代替稳定性验证。2026-09-09 实测发现 Node OOM，详见本轮报告（内部验收档案未随公开源码提供）。

先判定请求是否真实触发，再判定 UI 卡片是否到达，最后才执行批准/拒绝/回答。卡片缺失本身记失败发现；无法执行的后续用户动作按依赖记 blocked。重试前用崩溃时间核对前置仍成立，不能仅凭手机旧的“在线/运行中”状态认定任务仍在执行。
