所有分类都适用于 Codex、Claude Code、Kimi Code、Pi；按 Agent 分别记录结果，能力缺失保留失败/阻塞项，详见[Agent 参数矩阵](core-user-journey-cases.md#agent-参数矩阵所有核心-case-通用)。

P0/P1 表示原有使用优先级或用户指定必测级别，**不是功能分类**。同一功能有正常流程、异常流程和不同平台参数，不应直接把参数行数当成不同功能数。每次执行先列选中的编号和参数，结束逐条给结果。

## 页面入口与共用准备

本手册以**中文原生手机 App**为操作基线，依据当前 Flutter 页面及中文文案核对；不是本次逐页实测记录。Web、Windows 和各 Agent 入口存在差异，执行时记录实际按钮文字，不能套用手机路径宣称另一平台通过。

- **打开旧会话 S：**打开手机 Relayune → 点左上角「打开导航」→ 左侧选 Agent（如 Codex）→ 找到项目 → 展开会话列表（必要时点「展开更多会话」）→ 点 S 的标题。确认顶部项目、会话标题与 Agent 正确。
- **手机新建 S：**「打开导航」→ 选 Agent → 找到测试项目 → 点该项目的「＋ / 新会话」→ 进入空会话 → 在底部输入首条任务 → 点「发送」。当前手机新建直接使用默认会话名，**没有必填的“输入会话名”弹窗**；用首条消息中的唯一标记区分测试任务。
- **电脑发起 S：**在电脑的 **目标 Agent 原生 App/CLI** 中进入测试目录 → 新建测试会话 → 输入任务并发送（Codex 用 Codex App；Claude Code/Kimi Code/Pi 用各自原生 CLI）；再从手机导航找到同一任务。Relayune Desktop 是连接与授权入口，不能把在其概览页点击按钮当作“电脑发起 Agent 任务”。
- **打开配置：**进入 S → 点底部输入区上方的 Agent/模型配置入口 → 在该 Agent 的会话设置中选择实际支持的项。不要混同导航底部的 App「设置」。
- **打开 App 设置：**「打开导航」→ 底部账户区域的「设置」图标。账户菜单、会话设置、系统设置是三个不同入口。
- **统一夹具：**准备独立测试项目、会话 S/T、每轮不同的标记（例如 `QA-日期-随机串`），只在测试目录写文件。默认已登录、已配对、电脑在线。只有 A 类测试重新准备登录/授权，不让每条 case 重做配对。
- 表中的 **【测试准备】** 表示需独立测试账户、受控权限/网络/协议夹具等前置，**不是 App 里存在同名按钮**。无法构造前置时记录阻塞，不靠普通点击假装覆盖异常。

下面每行均给出起点、操作和终点。S/T 分别是两个测试会话，A/B 是两个独立授权客户端；“打开 S”“新建 S”使用上面的完整入口。

## A · 账户与连接

| Case | 从哪里开始 → 具体操作 | 到哪里结束 / 看什么 |
| --- | --- | --- |
| CORE-001-01 | 【测试准备】未绑定账户的电脑 Relayune → 登录入口 → 浏览器邮箱登录（首次用户按邮件设置密码，已有用户用密码）→ 确认电脑 → 返回 Relayune | 概览显示正确账户、电脑就绪；桌面登录不要求输入 8 位连接码 |
| CORE-001-02 | 【测试准备】测试 Agent 未安装或未登录 → Desktop「Agent」→ 点目标 Agent 查看状态及处理入口 | 原因准确；不能显示可执行。两种原因分别记录 |
| CORE-002-01 | Desktop「连接设备」（旧版本为「连接新客户端」）→ 显示本次二维码/8 位码；手机登录同一账户 → 配对页扫描，或「也可以输入 8 位码」→ 选择电脑 → 输入码 →「安全连接」→ 打开 S | 手机能读 S；Desktop 设备列表能识别该客户端。扫码、手输分开记录 |
| CORE-002-02 | 【测试准备】A 已配对，B 只完成邮箱登录 → B 尝试进入电脑工作区/打开 S、发送 | B 必须先授权；A 仍能使用；邮箱登录不等于获得电脑访问权 |
| CORE-003-01 | 测试登录页输入错误密码，或打开失效邮件链接；测试配对页输入错误/过期码 → 提交 | 留在对应登录/配对流程，有错误与重试入口；四种输入分别测，证据不保存凭据 |
| CORE-003-02 | 从上述已构造的错误页 → 使用正确密码/重新取得邮件链接，或 Desktop 生成新码后手机重新输入 → 提交 | 登录/连接成功，旧错误消失；不能只重新打开页面就算恢复 |
| CORE-004-01 | A/B 均已授权 → Desktop「管理设备」→ 选测试客户端 A → 撤销 → A 重新打开 S 并尝试发送；B 继续发送测试消息 | A 不能取新内容或执行；B 正常。A 已读缓存不要求被抹除 |
| CORE-004-02 | 从授权失效的 A → Desktop 重新生成码 → A 独立配对 → 打开 S → 发消息 | 新授权可用；【补充校验】旧凭据仍无效，不靠页面成功推断这一点 |
| CORE-024-01 | 已登录 A → 打开账户菜单/面板 → 再点账户入口或点外部关闭；支持键盘的端再测 Escape → 返回 S 发消息 | 账户仍登录、原会话可用。仅测当前端实际支持的关闭方式 |
| CORE-024-02 | A「打开导航」→ App「设置」→「退出登录」→ 确认 → 重开 A；B 打开 S | A 回登录页；B 不受影响。不要用共享 Desktop 退出替代 A 退出 |
| CORE-024-03 | A 退出后的登录页 → 重新登录 → 尝试打开 S | 按事前固定的授权保留策略恢复；无有效授权必须配对。策略未明确则先记阻塞 |

## F · 审批与回答

**审批前置：**在专用会话启用人工审批，任务请求在本轮独立路径写入唯一标记；事先确认文件不存在。必须真的出现待审批卡。普通文字“是否同意”不是工具审批。

**回答前置：**要求真实 Agent 调用结构化提问工具，设置可核对的选项/自由答案。必须出现可提交的问题卡，普通聊天回答不算。

| Case | 从哪里开始 → 具体操作 | 到哪里结束 / 看什么 |
| --- | --- | --- |
| CORE-013-01 | 打开待审批 S → 找到本轮卡片（折叠时展开处理过程）→ 读命令/差异 →「允许一次」→ 等结束 | 本轮完成，卡片显示已批准；电脑测试文件精确匹配标记，不能重复批准 |
| CORE-013-02 | 独立新路径的待审批卡 → 读命令 → 点当前 Agent 的拒绝动作 → 等终态 | 文件不存在，请求失效；仅卡片消失不算通过 |
| CORE-013-03 | A/B 同时保留同一审批 → A 批准 → B 提交旧决定 | 已处理/失效反馈；【文件校验】唯一标记只追加一次；旧视图必要时由受控夹具保留 |
| CORE-013-04 | **电脑目标 Agent 新建 S 并发送审批任务** → 手机导航打开同一 S → 读卡片 →「允许一次」→ 等完成 → 重开手机查看 | 原任务完成、文件精确匹配，待审批清除，已批准归入原轮过程，不复活 |
| CORE-013-05 | **手机导航→项目→新会话 S→发送审批任务** → 同一手机读卡片 →「允许一次」→ 等完成 → 重开查看 | 新建、审批、结果属于 S；文件及终态同上。不能拿电脑预建会话代替 |
| CORE-014-01 | 打开含结构化问题的 S → 选确定选项，或在「回答」输入框填标记 → 点问题卡的提交动作 → 等回复 | 实际答案被使用、问题已回答；不是往聊天输入框发送同一句话 |
| CORE-014-02 | S 的问题选答案但不提交 → 导航切到有不同问题的 T → 再回 S | S 的选择保留且没有带到 T |
| CORE-014-03 | A/B 保留同一问题 → A 提交答案 → B 尝试提交旧答案 | B 显示已处理，不执行第二次回答；必要时受控保留旧视图 |
| CORE-014-04 | **电脑目标 Agent 发起结构化提问任务** → 手机打开 S → 选择/输入答案 → 卡片提交 → 等完成 → 重开查看 | 原任务收到答案并继续，等待清除，已回答归入原轮过程；选项与自由输入分别出结果 |
| CORE-014-05 | **手机新会话 S→发送结构化提问任务** → 同一手机逐项回答 → 等完成 → 重开查看 | 问题/答案/结果都在 S，等待清除；同样分别测选项与自由输入 |

**CORE-014-05 多题参数的完整操作：**手机新建 → 请求两道选项题和一道自由输入题 → 按该 Agent 实际提问顺序逐题回答 → 检查三份答案都被使用 → 重开 App，已答题不复活。支持批量异步问题的 Agent 另测：保留三道未答题，切题检查草稿，再逐题提交；支持本轮结束后保留问题的 Agent 再验证该状态。同步问答不得要求先结束本轮再回答。选项按钮如果点击即提交，就按按钮直接验证；有独立「提交」按钮时再验证未提交草稿。基础的选项回答与自由输入对每个 Agent 均必测；批量、草稿、跨轮存续的能力差异单独记录，不能替代基础结果。中断/失败/过期的题不能再提交；键盘弹出时提交按钮仍可见。以上是同一 case 的参数，不另造编号。

审批/回答前先核验目标会话的实际权限模式；自动或无人值守模式可能自动处理审批并跳过提问，不能作为手动审批/回答的成功样本。Kimi 必要时显式选择 Default，再触发一次真实问题确认前置。

电脑/手机来源的审批和回答四条是用户指定的固定 P0。泛化用例 013-01/014-01 可共用同次操作的证据，但不能把复用证据算成额外四条来源链路。

## G · 停止与运行中发消息

**所有目标 Agent 的手机验收目标（并非当前能力保证）：**运行中直接发送新消息，会先停止旧执行，确认后在同一会话开始新轮次；不会等旧工具自然结束。下面四条按来源×动作分开测。

受控任务示例：`不要修改文件。运行 sleep 180，完成后回复 QA-OLD-本轮标记。` 等手机明确显示正在执行命令且原轮仍运行后再操作。Kimi 等 Agent 可能把命令放到后台并结束当前轮；此时先请求等待该受控后台任务，确认存在活动轮次，再执行停止/替换，不能把自然结束算停止成功。控制在 240 秒内，不拿用户真实长任务做试验。每次使用独立轮次。

| Case | 从哪里开始 → 具体操作 | 到哪里结束 / 看什么 |
| --- | --- | --- |
| CORE-015-04 | **电脑目标 Agent 新建 S→发送长任务** → 手机导航找到 S → 确认运行中 → 底部输入“停止旧等待，只回复 QA-NEW-标记”→ 点「发送」 | 旧轮已停止，新消息执行一次，出现新回复并空闲；辅助轮次日志证明旧中断早于新轮开始 |
| CORE-015-05 | **手机导航→项目→新会话 S→发送长任务** → 等实际运行 → 同一手机输入新指令 →「发送」 | 与上行相同，必须从手机新建起测；补测附件参数时核对内容、附件与消息编号不丢 |
| CORE-016-05 | **电脑目标 Agent 发起长任务** → 手机打开 S → 确认运行 → 点输入区「停止任务」→ 等「已停止」→ 再发一条普通问题 | 真实旧工具中断，停止入口消失/恢复输入，新消息可继续；T 若在运行仍继续 |
| CORE-016-06 | **手机新建 S→发送长任务** → 首次显示运行时立即检查输入区右下角（不等待列表刷新）→ 输入草稿，确认发送与停止都在 → 点方形「停止任务」→ 等已停止 → 再发送普通问题 | 空闲目录晚于实时开始事件到达时仍有停止入口；旧轮中断、旧审批失效、草稿保留、手机空闲，新轮可执行 |
| CORE-015-01 | 【非上述手机默认路径】先确认 Agent 支持即时补充 → 打开运行中 S → 输入带标记的补充 →「发送」 | 同一轮接受并在后续结果生效，不另开重复任务 |
| CORE-015-02 | 【其他明确支持排队的路径】打开运行中 S → 输入带标记的补充 →「发送」→ 看排队状态 → 等轮到它 | 先排队，再只执行一次；不要拿 任一 Agent 手机硬中断失败改判排队通过 |
| CORE-015-03 | 已确认既不支持即时补充也不支持排队的路径 → 打开运行中 S → 查看/尝试输入发送 | 禁用或限制说明明确，不悄悄丢内容 |
| CORE-016-01 | S/T 都在独立执行 → 打开 S →「停止任务」→ 再打开 T | S 真停止，T 仍运行；可复用来源专项的停止动作证据 |
| CORE-016-02 | S/T 各有待审批写入 → S「停止任务」→ 检查原审批 → 切 T | S 审批失效且文件不存在；T 审批仍可操作 |
| CORE-016-03 | 【协议时序准备】停止 S 旧轮 → S 发新任务 → 延迟投递旧轮状态/旧审批决定 → 观察当前 S | 新轮不被清掉，旧审批不执行；不能单靠随机点击证明竞态安全 |
| CORE-016-04 | 已停止、空闲的 S → 底部输入新问题 →「发送」 | 新轮回复，输入区没有残留忙碌锁；可共用 016-05/06 的最后一步证据 |

记录：点击停止/发送时间 → 旧轮终态 → 新轮开始（如有）→ 结果可见。若中断未确认，新消息不能暗中继续执行；正确回复但旧轮没停仍判失败。

## H · 子任务

这些场景先确认目标 Agent 支持委派。手机没有统一“创建子任务”按钮：通过主会话发送明确委派要求，并确认真实创建了两个子 Agent。只由主 Agent 自己完成不算。

| Case | 从哪里开始 → 具体操作 | 到哪里结束 / 看什么 |
| --- | --- | --- |
| CORE-019-01 | S 发送“委派两个子任务分别读取不同测试标记”→ 展开主会话子任务/Agent 工作区域（Kimi 可用「查看子 Agents」）→ 分别查看直到结束 | 两个独立任务、正确结果与归属，完成后仍能找回 |
| CORE-019-02 | 【测试准备】一个子任务成功、另一个受控失败 → 在 S 查看两个子任务结果 | 失败单独呈现，另一个不被污染，主任务不提前全完成 |
| CORE-019-03 | S/T 各有子任务，其中 S 子任务触发审批 → 在待处理入口点该审批 → 看所属主会话再处理 | 进入 S，命令与子任务来源明确，不出现在 T |
| CORE-019-04 | 【事前记录该 Agent 停止契约】S 及子任务正在执行 → S「停止任务」→ 展开子任务观察 → 切 T | 对应子任务按契约结束/收敛，不永久运行；其他主任务不受影响 |

## J · 离线、重开与失败恢复

## 怎样减少每次测试的操作量

1. 选功能分类与平台/Agent，列出具体编号和参数。只做专项时不用展开所有分类；完整核心回归仍执行约定范围。
2. 登录、授权、专用项目只准备一次；同次操作可引用到多个断言。例如 G 的停止后发送同时提供 CORE-016-04 证据，不再重复建一轮。
3. 保留**每个 Agent 八条来源明确的链路**：电脑/手机发起 × 手机审批、回答、停止、运行中发消息。它们验证不同接入路径，不能合成一条“手机可控制”。其中审批、回答、运行中发消息共六条 P0，停止两条 P1。
4. 需要异常夹具、第二客户端、真机的参数单列，准备不足就写明；不要把它们混进普通点击流程，也不在本次文档整理中取消它们。
5. 每条结果写“编号 + 端/Agent/来源 + 实际起止操作 + 预期/实际 + 证据 + 耗时”。历史通过只供参考，本手册不是新一轮测试报告。
