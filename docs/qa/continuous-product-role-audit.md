# Relayune 持续角色实访与产品评审

这套流程把真实用户任务和专业产品判断分开。每轮先由子 Agent 在本地与正式入口完成只读实访，
再由主 Agent 合并证据、实施最小改进，并让原角色回归复测。源码推断、自动化结果和真实浏览器证据
必须分别标注，不能互相冒充。

## 三类稳定用户角色

| ID | 用户角色 | 核心任务 | 成功标准 |
| --- | --- | --- | --- |
| `ROLE-NEW` | 首次使用的独立开发者 | 在 Mac 上安装 Relayune，并从手机继续第一个 Codex 任务 | 10 秒理解价值；无需理解令牌或密钥；按“桌面点击一次 → 登录邮箱 → 输入 8 位码”完成连接 |
| `ROLE-MOBILE` | 高频移动用户 | 在 Android、iPhone 或 iPad 上切换项目、查看状态、回复问题和处理审批 | 小屏单手可达；状态真实；断线可恢复；不会误操作高风险动作 |
| `ROLE-TEAM` | 安全敏感的团队技术负责人 | 判断能否在团队环境试用、部署、撤销客户端并恢复服务 | 安全承诺有边界；架构与公开说明一致；独立授权、回滚和数据责任可验证 |

角色描述保持稳定，便于跨版本比较。每轮可以补充网络、平台、语言和辅助技术等情境，但不得为了
解释当前实现而改写角色目标。

## 三种产品设计视角

| ID | 视角 | 首要问题 | 主要输出 |
| --- | --- | --- | --- |
| `LENS-PM` | 产品经理 | 用户是否快速获得明确价值，主动作与产品阶段是否诚实，学习成本是否低于收益 | 价值—动作断点、激活阻力、优先级与最小产品改进 |
| `LENS-DESIGN` | 交互/视觉设计师 | 信息层级、触达、反馈、焦点、响应式、动效和错误恢复是否支持真实任务 | 可复现的交互/视觉问题、视口证据与最小界面改进 |
| `LENS-ARCH` | 系统架构师 | UI 承诺是否符合生产拓扑、E2EE 不变量、授权边界、部署和回滚能力 | 承诺—实现差异、威胁边界、运维风险与验证建议 |

## 九宫格执行矩阵

三个角色都应接受三个视角的审查。日常快速轮次先执行对角线三个格子；发布准入或对角线发现 P0/P1
时，按三波补齐全部九格，每波最多三个并行子 Agent。

| 角色 \ 视角 | 产品经理 | 交互/视觉设计师 | 系统架构师 |
| --- | --- | --- | --- |
| `ROLE-NEW` | 首次价值与激活 | 首次连接层级与反馈 | 默认流程与协议边界 |
| `ROLE-MOBILE` | 高频任务效率 | 小屏、触控与恢复 | 移动密钥、通知与离线一致性 |
| `ROLE-TEAM` | 采用、定价与支持承诺 | 信任信息和管理入口 | 自托管、E2EE、撤销、部署与回滚 |

首次基线轮次使用 `ROLE-NEW × LENS-PM`、`ROLE-MOBILE × LENS-DESIGN`、
`ROLE-TEAM × LENS-ARCH`。后续轮次轮换对角线，避免长期只从同一种专业身份看同一用户。

## 子 Agent 实访契约

每个子 Agent 必须：

1. 先读取适用的 Browser skill，实际访问 `http://localhost:3000/`；需要核对已发布行为时，再只读访问
   `https://relayune.giraffetree.cn`。
2. 按角色完成一个端到端任务，而不是浏览所有页面。至少记录入口、主动作、一个恢复路径和退出/返回路径。
3. 不输入或提交真实/虚构邮箱、密码、验证码、8 位码，不读取 Cookie、IndexedDB 密钥、授权令牌或浏览器存储。
4. 对响应式问题记录视口、元素尺寸、页面滚动宽高和是否溢出；对交互问题记录操作、操作后状态和可见反馈。
5. 将结果分成“真实浏览器证据”“自动化证据”“源码/文档推断”。浏览器控制超时只记录为测试阻塞，
   不能直接定性为产品点击失败。
6. 只读审查，不并发修改文件。主 Agent 汇总后统一实施，避免相互覆盖。

固定回传格式：

- 角色、视角、平台、语言、视口和环境；
- 实际访问步骤；
- 可验证证据；
- `P0/P1/P2` 问题及每项最小改进；
- 做得好的地方；
- 一句 `GO / CONDITIONAL GO / NO-GO`；
- 未覆盖范围和证据限制。

## 优先级与合并规则

- `P0`：秘密泄露、错误授权、数据损坏、无法完成核心任务或没有安全恢复路径；阻断发布。
- `P1`：显著降低激活/高频效率、产生错误安全预期、公开承诺与实现冲突；进入当前优化轮次。
- `P2`：不阻断任务的层级、文案和精致度问题；进入候选池。

主 Agent 优先实施以下问题：两个以上独立角色/视角共同报告；违反 `AGENTS.md` 产品原则或安全不变量；
或单一证据已经构成 P0。纯审美偏好不得在没有任务影响证据时进入实现。

## 持续优化闭环

```text
角色任务与专业视角
        ↓
子 Agent 只读实访
        ↓
证据去重与 P0/P1/P2 分级
        ↓
主 Agent 实施最小改进 + 自动化契约
        ↓
原角色回归复测 + 仓库门禁
        ↓
记录仍有风险，轮换下一组九宫格
```

每轮结束应记录日期、版本/commit、执行过的矩阵格子、已修问题、未解决风险和下一轮入口。发布前仍须
执行`docs/production-release-lessons.md` 的对应发布门禁；角色实访不能替代密码学、桌面签名、真机和生产部署验收。

## 首轮基线（2026-08-14）

- 执行格子：`ROLE-NEW × LENS-PM`、`ROLE-MOBILE × LENS-DESIGN`、
  `ROLE-TEAM × LENS-ARCH`。
- 共同证据：默认扫码叙事与 8 位码默认路径冲突；macOS `0.2.9` 与 Android `0.3.1` 被一个全局
  “当前版本”混写；登录页品牌不是返回入口；“服务器只见密文”没有限定为业务载荷。
- 本轮策略：统一 8 位码为默认、扫码为快捷方式；按平台显示版本；让登录品牌返回当前语言首页；
  公开服务器元数据和 Web 前端完整性边界。
- 回归结果：三个原角色均确认各自 P1 修复；`390×844` 登录页返回路径和横向宽度通过，macOS
  下载按钮缺少版本的最后一项已补充源码与自动化契约。完整移动静态分析与 102 个 Flutter 测试通过。
- 未解决风险：公开站点仍缺面向团队的客户自托管可用性、责任边界、备份、升级和回滚说明；这是
  `ROLE-TEAM` 的下一项 P1。三步区标题换行和下载 CTA 附近的可核验安全入口为 P2 候选。
- 下一轮重点：补 `ROLE-NEW × LENS-DESIGN`、
  `ROLE-MOBILE × LENS-ARCH`、`ROLE-TEAM × LENS-PM`。
