# 一句话执行核心回归

**功能分类与 App 点击步骤：**[核心 case 操作手册](core-case-operation-guide.md)。先按功能选范围，再按本页约定执行与记录。

在 Relayune 项目中说：

> 跑一轮核心回归。

即执行下方完整约定，无需用户重复粘贴要求。这是 Agent 的任务入口，不是已经实现的一键测试脚本。用户当次指定的范围和限制优先。

| 口令 | 执行范围 |
| --- | --- |
| 跑一轮核心回归 / 跑核心 case（cases）/ 跑核心用例 / 测试核心用例 | 本轮全部 P0、P1；发现问题后修复并复测 |
| 继续核心回归 | 读取上轮记录，先处理 failed、blocked、not-run，再补齐剩余覆盖和受影响回归；保留此前有效证据 |
| 跑一轮核心回归，只测不改 | 相同测试与记录要求，不修改产品代码 |

每轮同时执行[提速与可恢复执行流程](core-regression-efficiency.md)：先统一预检并固定证据窗口，按供应商和连续旅程复用前置，逐步落盘检查点，精简证据读取，按阶段判断等待，集中修复安装与增量复测。
这是一套现在执行的工作约定；尚未实现一键编排器，不得报告为已有自动化。

## 完整执行约定

执行 Relayune 核心用户场景的真实回归，并完成测试记录、缺陷修复和相关复测。

1. **确定范围。** 阅读[核心测试树](core-user-journeys.md)、[可执行场景](core-user-journey-cases.md)、
   [链路顺序](core-test-execution-order.md)、[Agent 测试经验](agent-integration-testing-lessons.md)，以及
   `docs/qa/runs/` 中最近相关执行和修复报告。按叶子及其平台/Agent/示例参数冻结本轮 P0/P1 清单，
   不把旧报告的固定行数当成当前总数。沿用递进 80% 的使用优先级和用户明确指定的固定 P0，不自行重分级。
   固定 P0 必须包含 CORE-013-04/05、CORE-014-04/05：电脑发起/手机新建 × 手机审批/手机回答，每个目标 Agent 的四条分别出结果。
   同样按 Agent 必测 CORE-015-04/05（P0）与 CORE-016-05/06（P1）。默认矩阵 Codex、Claude Code、Kimi Code、Pi，用户指定子集优先；未支持的必测能力保留失败/阻塞记录，不静默跳过。
2. **确认实际版本。** 分别记录源码提交、已安装 Desktop/Web/iOS 版本与可核验的构建来源。
   默认验证包含最新相关修复的版本；按项目约定构建、安装所需本地版本，复用缓存和有效构建。
   Web 若与本地修复版本不同，单独记录；不得为了对齐版本擅自部署。
3. **保护共享环境。** iOS 模拟器操作统一使用 `$manage-ios-simulator-workflow` 及其 Relayune 安装适配。
   同时检查共享 `/Applications/Relayune.app` 是否正被其他任务安装、重启或验收；存在冲突时等待或协调，
   不反复覆盖、不停止他人任务。不同模拟器仍可能共用同一个 Desktop Relay。
   Agent 专项通过手机侧切换 Agent 执行，勿为选择测试对象把共享 Desktop 改成单 Agent 模式。
   测试必须临时改变该模式时记录原值，收尾恢复用户需要的模式并逐家验证会话列表；不能把测试配置遗留成日常配置。
   在链路切换及异常时复查 Desktop 进程和安装文件指纹；版本被替换后停止依赖该基线的验收，明确划分证据窗口。
4. **准备真实前置。** 使用本轮专用项目、会话、随机标记、图片和输出路径，主动准备缺失夹具。
   复用有效登录；待测分支需要配对时重新打开连接码，在有效期内输入和提交。不得复制凭据绕过授权。
   首次登录使用隔离实例，通知按用例的真机要求执行。不要因准备工作尚未做就标 blocked。
5. **按链路执行。** 先确认稳定在线，再按“项目与首轮 → 切换与草稿 → 阅读与结果 → 审批与控制 → 重连恢复”
   共享前置和操作；首次状态及系统通知保留独立链路。根据场景在 macOS Desktop、Web、QA iOS 间交替验证。
   每个叶子单独断言；一个平台或 Agent 的通过不代表其他参数通过。独立分支不因局部失败全部停测。
6. **验证真实行为。** 使用真实页面与真实 Agent。CLI 历史和协议测试是辅助证据，不能替代页面呈现、
   用户点击、跨端同步或文件副作用断言。审批验证请求归属、人工决定和精确副作用；回复验证实际显示及终态。
   稳定性检查记录 Relay PID、存活与 RSS，退出时保留脱敏证据，不靠反复重启掩盖故障。
7. **记录时间。** 每个场景记录开始、结束、耗时与结果；每项关键操作记录时间戳和耗时。
   能测量时分别记录发送到接受、首字显示、完成呈现、审批响应、历史加载和重连恢复的延迟。
   区分产品延迟、模型执行和自动化工具耗时；观察不连续时给出上下界，无法测得的值用 null 并说明原因，
   不填 0 或把单次观察称为 P95。共享操作只计一次，通过证据 ID 关联多个场景。
8. **如实判定并修复。** 执行后断言不成立记 failed；实际检查或尝试证明前置无法满足记 blocked，写明尝试、
   证据、依赖问题和解除条件；尚未执行记 not-run。例如卡片缺失本身失败，依赖卡片的批准动作可以 blocked。
   默认复现、定位并修复本轮发现的问题，按项目约定验证、提交和安装，再复测受影响的用户链路。
   保留首次失败和修复后结果，不因重试通过删除历史。不得推送、部署、公证或发布，除非用户另有明确指令。
9. **交付与收尾。** 在 `docs/qa/runs/` 新建本轮 Markdown 报告与机器可读的场景/操作记录，使用日期加轮次避免覆盖。
   至少保存用例 ID、参数、优先级、构建来源、状态、时间、证据引用和问题关联，不记录密码、连接码或密钥。
   更新测试树的最新执行入口及问题状态；最终汇报 P0/P1 各自的通过、失败、阻塞、未执行数量、主要性能、
   修复与剩余问题。释放自己的设备占用，保留无关用户改动；纯文档提交不构建 App。

执行过程中自主完成已授权的准备、修复和验证，不反复询问是否继续。确实缺少用户才能提供的输入、硬件或
共享资源时，明确缺口，并继续不依赖它的工作；不要把缺口转换成虚假的通过。
