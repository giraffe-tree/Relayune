# Relayune 核心使用场景清单

维护日期：2026-09-20。对应[核心测试树](core-user-journeys.md)。本文是可执行规格，所有场景初始为 `not-run`，不表示已自动化或已实测。

**按功能选择、逐步点击操作：先读[核心 case 操作手册](core-case-operation-guide.md)**。手册按账户连接、项目会话、消息配置、切换接续、图片阅读、审批回答、停止继续、子任务、通知、恢复十类组织；本页保留精确断言与参数边界。

`CORE-NNN` 保留原规则范围；`CORE-NNN-NN` 是可独立执行的叶子。每行只有一个被检验的行为；同一行为的相关结果可以有多个断言。一个规则下的行互不依赖，按需要各自准备前置状态。

## Agent 参数矩阵（所有核心 case 通用）

所有 case 都按目标 Agent 参数化，不再把来源链路限定为 Codex。默认目标为 `codex / claude / kimi / pi`；新增受支持 Agent 同样进入矩阵。用户明确指定子集时按子集执行。本轮范围内每个 case × Agent × 来源 × 客户端 × 必测变体独立记录；一个 Agent 的通过不能代表另一家。保留现有 78 个行为编号，不复制四套编号。

每个 Agent 必须展开八条来源链路：CORE-013-04/05（审批）、CORE-014-04/05（回答）、CORE-015-04/05（运行中发送并中断后继续）、CORE-016-05/06（停止）。前六条 P0，后两条 P1；四家合计 32 条基础参数行，问题类型、多题和客户端参数另计。拒绝、旧请求失效、停止待审批等泛化异常 case 也按各 Agent 执行，不被这八条代替。

“电脑发起”指该 Agent 在电脑上的原生 App/CLI 发起，由该原生进程持有执行；“手机发起”必须从手机新建会话开始。电脑浏览器经 Relay 发起、或脚本调用 Relay 适配器的任务可作补充，但不得冒充原生 owner 跨端控制已通过。

能力缺失不能静默删除必测行：未安装、未登录等使真实前置无法成立记 `blocked`；用户已能执行动作但产品未达到要求记 `failed`；分别记录 `capability_gap`、证据及待解决能力。八条必测链路不因当前未实现而改为不适用。仅对原规格明确限定能力的可选参数保留不适用，且说明依据。普通文本对话不代替结构化回答，steering/排队不代替硬中断。这里定义验收目标，不宣称所有接入已支持。

## 使用优先级

遵循[核心测试树的递进 80% 定义](core-user-journeys.md)：P0 / P1 / P2 / P3 分别对应目标使用量 80% / 16% / 3.2% / 0.64%，目前是基于日常使用主线的频率假设。每行显式标注使用优先级；规则标题只汇总包含的级别，不对子项统一赋值。故障影响及专项必测要求不由该级别代替。

部分参数组合频率不同，使用下面的覆盖值；其余参数沿用场景行级别：

| 场景 | 示例参数 | 使用优先级 | 依据 |
| --- | --- | --- | --- |
| CORE-010-01 | 不同 Agent | P1 | 跨 Agent 切换少于日常同 Agent 会话切换 |
| CORE-012-01 | 文字加图片草稿 | P1 | 附图属于较少发生的输入方式；纯文字草稿为 P0 |
| CORE-022-01 | 正常重启 Desktop | P1 | 重启电脑端应用少于手机重开或 Web 刷新 |

运行结果记录最终使用的参数级别，不能把这些 P1 组合计入 P0 通过数。不同客户端或 Agent 的用户群有明显频率差异时，先固定人群，再校准分级。

## 共用夹具与判定口径

- **客户端 A/B**：独立登录、独立授权的测试 Web 或手机客户端。**会话 S/T**：独立测试会话，各用独立目录及本轮随机标记。只有验证跨端同一会话时才让 A/B 共享 S。
- 正常场景默认电脑和相应真实 Agent 就绪、客户端已授权；登录或授权测试显式覆盖这个默认值。只准备当前行需要的项目、客户端和数据，不要求每条都初始化全套设备。
- 写入只发生在本轮目录；批准、拒绝和停止分别用新的输出路径。清理只涉及本轮拥有的资源。人工审批模式在测试会话内明确设置，不修改全局权限；必须先确认真实审批到达，再执行审批动作。
- **等待结束**：等待对应会话/轮次的真实终态，使用运行前记录的超时上限。未等到终态不能判“未执行成功”；超时保留失败或阻塞原因。界面完成、真实执行与文件核对分别留证。
- **示例矩阵**：表中用 `<参数>` 的行，按该规则下列出的值展开，每个组合独立出结果。能力、限额和处理模式在运行前依据实际版本固定，不根据运行结果临时换成更宽松的期望。
- 默认执行组合记录电脑系统、客户端、Agent 与真实版本；iOS/Android 必须注明真机或模拟器。桌面账户登录的详细操作以 macOS 为基线；Windows 使用对应专项。

### CORE-013 · P0/P1/P3 · 批准才执行，拒绝无副作用

| CORE-014-03 | P3 | A 已回答某问题，B 持有旧问题视图 | B 尝试重复回答 | 不触发第二次回答执行，原问题呈现已处理状态 |

示例：`问题类型 = 选项 / 自由输入`，仅按真实能力执行。每个目标 Agent 的 CORE-014-04/05 分别记录两种输入的结果；能力不可用时写明失败或阻塞证据，不能静默省略。

CORE-014-05 必测多题变体：手机新建任务，一次发出三道异步结构化问题（两道选项、一道自由输入），Agent 随后正常结束轮次。确认未答题仍可回答；切换题号保留各题草稿；逐题提交后进度推进，三份实际答案都送达同一会话，且不重复启动轮次。重启恢复仍在有效期内的未答题，已回答项不得复活。题目按原顺序展示，一次显示一道，键盘不能遮住提交按钮。中断、失败、过期的问题不可继续提交。

#### 四条手机决定链路：固定 P0 核心 case

2026-09-20 按用户要求推广到每个目标 Agent：CORE-013-04/05、CORE-014-04/05 为 P0，每轮核心回归必须按 Agent 分别逐条列出和验收。对应历史六条场景 C1、C2、C4、C5；电脑端处理的 C3/C6 不包含在本次新增范围。手机新建是完整链路前置，不能用电脑预建会话代替，也不因通用“新建会话”级别为 P1 而降低这两条链路的 P0。

共同验收要求：

- 使用真实目标 Agent、真实手机页面和实际用户操作，记录会话 ID、轮次、请求 ID、客户端/Agent 版本及关键耗时。工具夹具通过不代替真实链路通过。
- 审批必须核验批准前无写入、批准后精确文件副作用；提问必须核验 Agent 收到实际答案并继续，普通文本问答不算结构化提问。
- 完成的请求归入原轮次“处理过程”并折叠，不能独立堆在最终回复后；命令显示“已批准”，问题显示“已回答”。重开 App 后不得复活待处理卡或重复执行。
- 四条独立出结果，不以其中一条替代另一条。与 CORE-013-01/014-01 共用操作时关联同一证据，泛化断言不重复计作第五/第六条跨端链路。
- 当前已有协议与 Flutter 审批组件回归，真实链路仍需页面验收；历史结果见手机修复报告（内部验收档案未随公开源码提供）及展示修复记录（内部验收档案未随公开源码提供）。本次分级更新不代表重新验收通过。

所有目标 Agent 运行中手机发送约定（2026-09-20 泛化）：CORE-015-04/05 是“中断旧执行，再开始新轮次”，不能用普通 steering 或等旧轮完成后的排队代替。中断未确认时不自动发送新消息，显示失败并保留可恢复输入/记录。两条分别记录，真实页面点击、旧轮次终态、新轮次标记与唯一消息编号共同作为证据。

| ID | 优先级 | 前置 | 操作 | 断言 |
| --- | --- | --- | --- | --- |
| CORE-016-05 | P1 | 目标 Agent 电脑端发起专用受控长任务 | 手机点击停止 | 停止入口可用；旧轮次到达 interrupted，长工具被中断；手机停止等待，另一个会话继续；随后可发送新消息 |
| CORE-016-06 | P1 | 手机新建目标 Agent 会话并发起专用受控长任务 | 同一手机点击停止 | 同一轮次到达 interrupted，手机恢复空闲，旧审批失效；停止后的新消息可正常执行 |

CORE-016-03 优先使用可控协议时序，再对已发现的真实问题复验；不靠随机等待碰撞时序。

| --- | --- | --- | --- | --- |
