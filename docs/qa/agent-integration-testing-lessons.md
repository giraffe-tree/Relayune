# Agent 接入测试经验与自动化路线

来源：2026-09-08 对 Codex、Kimi Code、Claude Code 的逐项实测。
[当次版本、结果和重跑命令](../agent-live-verification.md)保留为验收记录；本文沉淀后续接入、修复和自动化可复用的方法。

## 1. 从这次测试中确认的经验

### 真实 CLI 与协议夹具各有不可替代的作用

最初 104 项适配器及项目管理测试通过，真实 Kimi 审批仍暴露了字段形态差异：
请求没有 `rawInput`，命令在 `content` 中，工具标题只是 Bash。
适配器优先展示标题，导致用户看不到自己批准的操作。

做法：先跑确定性测试建立基线，再通过产品实际适配器调用真实 CLI；
发现真实差异后，将最小协议形态加入夹具或直接输入测试，先复现失败，再修复、回归和真实复验。
保留工具标题但省略 `rawInput` 的命令和文件 diff 已加入
[Kimi 合约测试](../../tests/kimi-contract.test.mjs)。
不能只让假 CLI 模仿我们希望收到的消息。

### 审批要同时验证请求、决定和副作用

“模型说写好了”与“文件确实存在”都不足以证明审批链路可用。此次 Kimi 首次写文件没有产生审批请求，
而显式设置测试会话为 default 后产生了请求。未单独证明首次行为的根因，不应把它记录成确定的上游缺陷。

后续固定验证：

1. 会话采用可确认的人工审批模式；不修改用户的全局权限设置。
2. 收到属于当前 provider、session、turn 的审批，请求包含可理解的命令或差异。
3. 批准后检查精确文件内容；拒绝后确认文件不存在。
4. 等待审批时停止，确认轮次结束、旧审批不可再提交、文件不存在，再验证能继续对话。
5. 同时保留另一个会话的待审批记录，确认清理不越界。

Codex 实际会把命令包装成 `/bin/zsh -lc '…'`；Claude 的显示带 `Bash:` 前缀；
此次 Kimi 的显示来自审批说明。测试脚本的最初精确白名单拒绝了合法包装，属于测试适配问题。
应核对真实载荷后增加明确允许的等价形式，不能为通过测试而放宽成“包含 printf 就批准”。
未来优先按结构化命令、参数、工作目录校验；只有显示文本的协议保留窄白名单，未知形式拒绝并报告。

### 并发问题用可控时序复现

Kimi 原来在 `await ensureSessionActive()` 前检查运行状态，之后才登记轮次。
两个发送都可能越过检查，重复启动并覆盖当前轮次。普通逐轮对话不会触发这个问题。

此次测试用可手动释放的 Promise 阻塞会话加载，连续调用两次发送后再释放，
明确断言第二条被拒绝且只出现一次 `turn.started`。修复是在首次异步等待前预留启动状态。
同组测试还覆盖加载失败后重试、加载中关闭、关闭后发送。

经验：用屏障控制竞争窗口，不靠随机 sleep 或重复跑很多次碰运气；
同时断言“错误被报告”和“不会残留锁、重复请求或不可恢复的运行状态”。

### 停止按钮成功不等于生命周期结束

Kimi 中断后能发出结束事件，但 `pendingApprovals` 仍保留旧记录。
修复按会话清理和取消待审批，并测试迟到的批准被拒绝、其他会话审批保留。

将以下过程视为完整用例：运行 → 等待审批 → 停止 → 审批失效 → 空闲 → 再次发送。
后续应扩展到 CLI 崩溃、连接断开、超时、子 agent 中断和结束事件重复到达。
同一轮的终态应幂等，旧轮次的迟到事件不能清除新轮次或污染其内容。

### 使用应用实际解析到的二进制

本机 PATH 的 npm Codex 缺少 vendor 二进制，但 Relayune 优先解析的 ChatGPT 内置 Codex 可用。
只运行 `command -v` 或 PATH 中的 `--version` 会误判产品不可用。

预检需要记录适配器最终选择的路径、版本、能力和登录可用性。
环境问题与产品缺陷分开报告，不自动升级 CLI、修改全局安装或用户凭据。
版本升级后优先复测审批形态、子 agent 事件、历史与恢复能力。

### 测试应跟随契约，而非文件布局

Web 回归仍要求页面内声明 `AgentProvider`，实际已迁移到共享模块。这次修正了测试来源。
后续能执行行为的地方优先断言导出值、路由或渲染结果；源码正则仅用于确有必要的结构约束。
代码搬家导致测试失败时，先确认产品行为，再更新断言，不能简单删掉失败项。

## 3. 后续自动化分层（待实施）

| 层级 | 触发方式 | 核心断言 | 执行条件 |
| --- | --- | --- | --- |
| 确定性合约回归 | 相关 PR/本地修改 | 字段变体、审批归属、并发、失败恢复、事件幂等、项目重试 | 假 CLI、临时目录；无需真实登录或模型额度 |
| 真实 CLI 冒烟 | 手动；后续可在受控机器每日执行、CLI 升级后执行 | 真实请求与响应、文件副作用、目录和历史回读、重启后上下文 | 已登录的专用测试账户；固定预算；三家顺序执行 |
| 原生多 agent 专项 | 子 agent 接入改动、CLI 升级后 | 至少两个子 agent 的独立 ID、完成快照、审批归属、部分失败与父任务中断 | 测试任务可分解、无外部副作用；单独限制耗时与额度 |
| Web/原生页面旅程 | 相关 UI 或跨端状态逻辑变更后 | 选 provider、建项目/会话、审批卡动作、运行/停止状态、刷新恢复 | 测试环境与已配对客户端；不复用生产会话 |

先实现合约回归与真实 CLI 编排，再扩展多 agent 和页面旅程。
自动化测试不附带发版、部署或上传权限，真实 CLI 测试也不接入普通无凭据 CI。
若需原生本机验收，仍遵循根 AGENTS.md 的最终提交构建、安装路径及隔离要求。

### 第一阶段：将现有脚本变成可恢复的批次任务

当前人工/Agent 执行已采用[核心回归提速流程](core-regression-efficiency.md)的预检、检查点、截止时间和时间分类；
下述编排器开发应复用这份格式及规则，避免另建一套冲突约定。脚本尚未自动实现的部分不得报告为已自动化。

建议增加独立编排器，复用现有脚本，不重写三套同样的场景：

1. 生成 `run_id`，记录 Git 提交、平台、provider、实际 CLI 路径和版本，执行登录与能力预检。
2. 为每个 provider 创建独立项目和 fixture；按 Codex → Kimi → Claude 顺序执行基础流程。
3. 每个步骤立即写检查点；成功创建会话后就保存其 ID 和目录，不等整套完成才保存。
4. 基础流程通过后，启动新的进程执行 `--recover`，自动传递检查点中的参数。
5. 一家失败仍继续其他家的独立流程；依赖失败步骤的后续用例标为 blocked，不假定成功继续。
6. 每家关闭其测试子进程，汇总用例矩阵和失败原因。失败产物先保留，清理只涉及有所有权标记的测试资源。

完成标准：一次命令得到三家基础与恢复结果，无需手工复制 sessionId；
批次被中断后能识别已完成步骤；失败的一家不隐藏其他家的结果。
定时执行前先完成预算、进程超时和资源回收机制，不直接把当前脚本放入无限重试的定时器。

### 报告与失败分类

建议每条结果包含：`run_id`、`case_id`、`provider`、`phase`、`status`、
`duration_ms`、`attempt`、`failure_category` 和本地证据引用。
批次元数据包含提交、CLI 版本、实际权限模式与支持的能力；本地检查点另存 fixture 路径和会话 ID。
这是未来报告格式，当前脚本尚未输出全部字段。

状态至少区分 passed、failed、blocked、skipped；未登录、额度耗尽、缺少所需能力不能算通过。
失败分类建议包括环境、鉴权、额度/限流、协议/适配器、模型未按要求调用工具、测试脚本、超时。
分类必须来自证据；无法定位的超时保持未知，不擅自归因上游。

重试只针对可识别的暂时性错误，建议最多一次，并保留首次失败。
重新运行写文件、拒绝和中断测试应使用新的 fixture 文件，防止旧文件造成假阳性或假阴性。
协议错误、越权副作用、并发覆盖等确定性失败不得靠重试变绿。
单轮现有等待上限为 180 秒；编排器还需全流程墙钟上限、关闭宽限期及预算耗尽后的停止策略。

### 收紧断言，减少模型随机性的影响

- 每次运行生成不同的记忆标记；第二轮只询问标记，不把答案再放入提示。
  当前固定标记可验证基本流程，后续随机化可降低历史污染的风险。
- 流式输出、终态、审批和子 agent 事件按 provider/session/turn/agent ID 关联。
  不能用“这一段时间出现过一个完成事件”证明当前任务完成。
- 保留协议、真实副作用和回读三类证据。模型最终说“已完成”只作为辅助。
- 会话隔离做双向检查：A、B 各自记住不同标记，交替询问并在新进程中恢复后再询问。
  当前恢复脚本只检查新会话为空、写入 B 后 A 保持原标记，需要继续补强。
- 子 agent 测试记录委派前后的任务 ID 差集；只接受本轮新任务的完成状态。
  至少两个任务分别读取不同 fixture，再检查输出归属。补充一项失败不污染另一项的场景。
- 对“不支持”的能力单独报告；不能用主 agent 直接完成工作冒充子 agent 通过。

### 测试数据与日志

只使用生成的 fixture 内容，报告默认保存版本、状态、耗时及脱敏事件摘要。
现有脚本会输出测试审批说明和本地临时路径；接入集中报告前需收窄日志字段。
原始事件如确需保存，应限本机受限文件、只含测试会话，并设保留期；不提交真实用户历史。
任何层级都不得记录 token、Cookie、PAKE 短码、内容密钥或凭据。
跨端测试继续满足[架构与安全约束](../security-and-architecture.md)，不为观察数据让 Server 接收会话明文。

## 4. 下次接入修改的执行顺序

1. 确认实际二进制、版本、能力、临时项目和测试账户，选择本次影响的用例。
2. 跑相关确定性回归，再逐家执行真实流程；记录失败原始现象与所属层级。
3. 产品问题先加入会失败的回归，再修复；测试问题修正断言或夹具，不扩大执行权限。
4. 在相同已知失败条件下复验，确认恢复路径和其他会话未受影响。
5. 汇总通过、失败、阻塞和未覆盖项，更新当次记录，提交代码与经验；只有明确授权才推送或发布。
