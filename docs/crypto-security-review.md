# 会话内容保密审查与独立审计范围

审查日期：2026-10-22。基线为 `aaa805946b4cb828db4e4922fc2598504f3eacc9`，并检查本轮删除飞书及 Relay 旧共享密钥入口后的工作区。**这是与改造实现分工的 AI 源码复核和合成对抗验证，不是独立第三方专业密码学或侧信道审计，也不构成“绝不会泄密”的证明。** 不应将依赖库通过审计或 RFC 向量通过写成 Relayune 已通过整应用安全审计。

范围更新：2026-10-23 维护者明确，本次关注 Codex 会话内容在正常 Relayune 中转链路中的保密，
不要求第三方密码学验证。下文保留审查发现与未验证边界；专业外审范围仅供未来选择，不是当前待委托任务或公开门槛。

## 当前能支持的结论

保护对象是任务会话正文、Agent 输出、历史、项目路径、文件/图片和审批动作。客户端在进入会话 API 前加密，Desktop Relay/客户端在本地解密；账户认证与路由不需要这些内容密钥。此次真实隔离服务验证中，服务端收到和保存的是这些业务数据的密文，未发现通过已检查路径导出内容密钥或会话明文的行为。

这个结论有明确前提：使用未被替换的客户端、可靠的随机源、正确完成独立 PAKE，客户端及签名/更新密钥没有失陷。**若攻击者同时能替换 Web 客户端的 JavaScript，当前 Web 版本不能保证会话内容对它保密。** 原生客户端减少了这项依赖，但其协议组合、撤销模型和真实设备侧信道仍需要专业审计。

## 按攻击者能力区分

| 攻击者拿到什么 | 对任务会话内容的判断 | 仍然可见或不在保证内的内容 |
| --- | --- | --- |
| 当前协议写入的 Mongo 文档、私有 blob、备份副本、规范日志 | 未发现其中包含任务明文、短码、PAKE 私密状态或内容密钥；仅凭已记录公开 PAKE 消息不应能离线验证短码猜测 | 账户信息、随机路由标识、时序、包大小、在线状态及用户主动反馈；本次未扫描生产历史备份 |
| 运行中的服务端进程、TLS 终止点和服务配置 | 正常原生客户端的任务内容仍在客户端加密，Server 没有业务解密密钥的设计入口 | Server 会瞬时处理登录密码和账户/设备/客户端 bearer 等认证凭据；不能把“只存摘要”说成“运行时从未见过” |
| 可改写 API、Mongo、握手及中转密文的恶意 Server，客户端代码保持可信 | 错误口令、替换配对编号/share、篡改 AAD、伪造另一客户端 `kid` 的合成攻击被拒绝；不能据此声称覆盖所有主动攻击 | 可拒绝服务、删除/延迟/重放密文、伪造在线状态；授权列表与撤销仍有服务端信任边界，见下文 |
| 上述 Server 还能替换 Web HTML/JS | **当前 Web 不满足这一强威胁模型** | 恶意同源代码能调用已有 CryptoKey 解密，再外传明文或截取新输入；HTTPS/CSP/不可导出密钥不能阻止代码提供方自身作恶 |
| 获得 Desktop/手机/浏览器运行权限、内容密钥、Agent 权限或发布签名私钥 | 不在当前中转保密保证内 | 端点本来就要读取明文；静态内容密钥失陷后可解此前录制的对应密文 |

账户密码、邮箱、公开版本、设备名称、路由/流量元数据与用户**明确主动提交的反馈**分别遵守对应规则；主动反馈正文、图片、可选联系方式是可读数据，不能拿它承诺会话端到端加密。客户端不应自动把会话或原始日志加入反馈。详见 [威胁模型](e2ee-threat-model.md)、[反馈规则](feedback.md) 和 [HTTP 日志](request-log-v2.md)。

## 已检查的实现

| 环节 | 源码与检查结果 |
| --- | --- |
| 短码与 PAKE | `shared/pairing-pake.ts`、`shared/spake2-p256.ts` 与 Mobile 对应实现：32 字符的 8 位随机码（40 bit）、配对编号盐、scrypt N=32768/r=8/p=1、固定 P-256 M/N、有效点检查、双向 HMAC 确认、完成后才采用新密钥 |
| 内容密钥 | 每个客户端独立 PAKE；从 RFC 的 16 字节会话密钥通过专用 HKDF info 扩展为 32 字节 AES 密钥。扩展长度不增加原有熵，不能宣称整个协议具有 256 bit 安全强度 |
| 业务密文 | `relay/e2ee.mjs`、`app/e2ee.ts`、Mobile `crypto/e2ee.dart`：AES-256-GCM、96 bit 随机 IV、128 bit tag；AAD 绑定方向、类型、设备、会话、请求、事件序号及时间 |
| 独立客户端 | Relay 现在只接受精确本地 `browser_id` 与密钥摘要绑定；拒绝同一密钥关联多个客户端。Server 不能只报一个已知 `kid` 就制造另一个可用接收方 |
| HTTP/WSS/WebRTC | `relay/mac-relay.mjs` 与现有传输测试：服务器链路与直连仍使用同一认证密文；写操作去重记录和原始请求编号用于回退，不以换编号重发来绕过结果未知状态 |
| Server/Mongo/blob | `server/pairing-api.ts`、`server/relay-api.ts`、`server/mongo-store.ts`、`server/relay-blob-store.ts`：握手存公开值/确认值，业务路由严格接收 envelope；大命令和响应 blob 仍是 envelope，私有目录不作为静态资源 |
| 日志与推送 | `server/request-log.mjs` 只序列化白名单；iOS 任务摘要使用派生推送密钥加密，APNs/JPush 目的令牌属于服务端可处理的投递凭据；Android 供应商仅收到通用提示与不透明回执，不收到任务正文 |
| 更新信任 | Desktop 固定 updater 公钥、原生应用签名与系统安装校验提供独立信任根；这不自动等于完整抗回滚、可复现构建或签名密钥失陷保护。本轮没有新安装、签名或发布任何应用 |

PAKE 的安全性质以正确的协议和实现为前提，不能通过有限猜测测试“证明无法离线攻击”。本次核对使用 [RFC 9382](https://www.rfc-editor.org/rfc/rfc9382.html) 的公式、参数和向量；该 RFC 是 Informational 文档。AES-GCM 的唯一 IV 与认证要求依据 [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)。

## 本次发现与处理状态

1. **旧共享密钥入口已移除。** 原先 Relay 可把无 `browser_id` 的单个 key 存入 `legacyKeysById`，再按 Server 提供的 `kid` 绑定任意客户端编号。这会破坏“每客户端独立密钥”的不变量；不是 Server 能从摘要反推出密钥，也不代表正常 Desktop 的独立 PAKE 已泄露。本轮删除该分支，启动和动态更新均拒绝重复 key/客户端，测试覆盖拒绝发生在 Agent、网络和持久状态启动之前。
2. **Web 主动代码替换边界仍存在。** 新测试证明 `exportKey` 失败的同一不可导出 CryptoKey 仍可执行 `decrypt` 并得到明文。这与 [Web Cryptography 规范的密钥用途和可导出属性](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/#cryptokey-interface) 一致。若要把“掌控中转 Server 也拿不到会话”扩展到网页，需增加独立可信的客户端代码分发/校验机制；本轮没有擅自关闭 Web。
3. **撤销仍有主动 Server 边界，已用真实业务方法复现。** 对合成授权调用 `syncBrowserAuthorizations([])` 后，真实 `writeEvent` 不再生成副本；回放旧授权快照后，尚在本地登记的 key 重新激活，`writeEvent` 生成的新密文可被持旧 key 的客户端解开。Desktop 显式 `updateBrowserKey(id, null)` 删除本地 key 后，相同快照回放不再生成副本。Web/手机侧撤销或暂时从快照消失不等同于 Desktop 已永久销毁该 key。Server 自身仍不由此得到 key；抵抗“恶意 Server 与旧授权客户端串谋”需要本地不可回退撤销记录/可信确认机制及单独审计，不能当成已经完成。
4. **侧信道审计未完成。** 本轮锁定的 `elliptic 0.4.0` 已采用 Montgomery ladder 与无秘密位条件分支的交换；不能套用旧版本的简单 double-and-add 描述。其 Dart `BigInt` 运算仍没有硬性常量时间保证。`@noble/curves 2.3.0` 使用秘密标量保护，但其官方也明确 JIT/GC/BigInt 和内存清理的限制。依赖的改进不等于 Relayune 的 scrypt、PAKE、UI、Isolate 和设备整链路已通过评估。[elliptic 上游](https://github.com/c0mm4nd/dart-elliptic)、[noble 2.3.0 安全说明](https://github.com/paulmillr/noble-curves/blob/2.3.0/README.md#constant-timeness)
5. **没有逐消息前向保密/ratchet。** 同一个已配对客户端持续使用内容密钥；新测试明确演示“后来拿到内容密钥可解此前录制的对应密文”。这不同于“仅掌控 Server 可解密”。密钥使用量上限、重配/轮换和旧密钥销毁策略应纳入后续协议评估；随机 IV 抽样不构成全生命周期唯一性证明。

## 未来如选择专业外审，可采用的范围

本次不委托专业外审。此前仅准备了以下可选范围，没有联系外部团队、上传代码/数据、采购或产生审计费用。

- **冻结对象：** 指定审计提交、全部锁文件、JS/Dart/native 工具链、构建参数及各正式客户端二进制指纹；源码审查与二进制验证要对应同一版本。
- **协议审查：** RFC 9382 profile、口令到标量映射、M/N/点编码与无效点、身份/实例绑定、确认顺序、熵和随机源、密钥隔离/派生/销毁；给出主动恶意 Server、并发配对和在线猜码下的分析。
- **业务保密审查：** 用户输入、模型/工具输出、审批、文件/图片、目录/历史、本地预览、错误和取消路径；逐项验证加密发生在出站前，没有明文 fallback、日志/监控/反馈自动附带或推送泄漏。
- **身份及状态攻击：** 精确客户端与实例绑定、授权快照回滚、旧客户端串谋、撤销/重配/重启、请求/审批/回执重放、乱序、WebRTC 与 HTTPS 同时到达、失效/崩溃后的未知执行状态。
- **侧信道：** 至少覆盖正式发布配置的 iOS/Android AOT 与 Desktop/Web 实际运行时，明确本地共驻攻击和远程时序攻击分别能观测什么；使用稀疏/密集/边界标量、攻击者可控有效点、口令类别与随机化采样顺序；预先说明采样量、统计功效、重复试验和多重比较策略，交付原始样本与可复跑工具。单次平均耗时、模拟器、JIT CLI benchmark 或未发现统计差异均不能宣称常量时间。
- **代码/更新信任：** 恶意网页分发的可实现防护边界、发布密钥隔离、验签/降级/回滚、依赖溯源；明确“服务端失陷”和“发布签名私钥失陷”是两个攻击模型。
- **交付验收：** 报告写清审计者、资质/独立性、版本、工时/方法/排除项、每个发现的影响与复现、修复建议、修复后复测及残余风险；高风险内容保密问题在关闭前不能标为审计通过。可公开摘要与私密细节分开，不公开真实凭据或用户数据。

完成并复测后，再据报告收紧或扩大安全承诺。源码公开、安装包通过签名、工程测试通过与专业安全审计是不同的交付状态。
