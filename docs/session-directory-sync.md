# 手机会话目录定时同步

Desktop 在内存维护各 Agent 合计最近最多 300 条会话记录，按更新时间倒序排列。
这是远程目录上限，不删除 Agent 原生会话或聊天历史。Codex 原生列表按 100 条分页读取到
最多 300 条；Claude 的读取上限也为 300。Kimi/OpenCode 遍历原生分页但仅保留最新 300 条，
避免源端未排序时漏掉新会话；各 Agent 合并后再次全局裁剪。
Desktop 每秒尝试刷新目录，同一轮未完成时复用在途读取，不排队积压。

手机只有前台定时器会发起目录同步，每秒最多启动一轮，上一轮未结束时跳过该次触发。
点击项目、加载更多和重新展开只读取手机已经同步的数据；每次多显示 5 条。
应用退到后台暂停目录定时器，回到前台立即请求一批，再恢复每秒同步。
恢复时使用已有配对凭据并行启动目录同步、实时连接与 bootstrap 元数据/事件刷新；
不等待 bootstrap，也不在其完成后取消正在进行的目录请求。聊天正文、附件和用户写操作仍沿用原有链路。

## 加密协议与增量

复用 `project.sessions` 加密请求，载荷带 `directory_sync: true`、已完成的 `revision`
以及可空 `cursor`，新版手机另带 `batch_size: 300`。响应为原有 `project.result` 内的 `directory` 对象，不新增服务端明文字段。
新能力由加密目录里的 `desktop.session_directory_version: 1` 声明。

- 新版手机首次同步一批最多 300 条，可一次取得整个有界目录；旧手机未声明批量大小时仍为 50 条。
  新手机连接旧 Desktop 时仍接受原有分页；保存中的旧游标也可用更大批次接着读取同一快照。
  目录摘要只含 ID、标题、项目路径、更新时间、运行状态等字段，
  不携带聊天正文、附件或完整模型配置菜单。
- 之后根据上次完成的版本只返回新增/修改记录、移出目录的 ID，以及有变化的项目列表。
- 没有变化时返回空变化集和当前版本，不重新发送 300 条记录。
- 分批同步固定在不可变快照上，收到最后一批才推进完成版本；途中断网重试同一检查点。
- Desktop 保留最多 32 个版本快照以支持分页及差异计算；过期版本或 Desktop 重启触发明确重置，
  手机清理旧目录后分批重建，不能拼接不同版本的页面。
- 缓存请求直接读取内存，不等待原生 Agent 查询，也不排队等待项目创建/文件浏览操作。

授权后采用增量同步的手机不再接收包含会话列表的旧版定期 catalog；旧 catalog 只用于
Desktop/Agent 能力和用量等元数据。初次授权及旧客户端保留最多 50 条的兼容目录；Web 的
原有项目分页接口继续工作。旧 Desktop 未声明新能力时，手机只通过定时器处理 catalog
失效通知，不回退到点击触发上游查询。

初次配对的兼容目录同样不重复携带各会话的完整模型/权限配置菜单；当前模型及能力字段保留，
完整选项随打开会话后的现有加密详情响应提供。否则 50 份重复菜单加上 Base64 开销可能超过
catalog 的 512,000 字节上限，导致电脑已在线、配对已确认，手机却始终等不到首个加密目录。

## 手机持久化与状态

目录和分页检查点作为独立记录类型写入现有 AES-256-GCM 加密追加存储，按账户、Desktop
和授权密钥隔离。连续变化的磁盘写入合并到最多每 5 秒一次，退到后台时刷新待写数据。
已经打开的会话和刚创建的会话仍遵守原有选择保留规则，不因为移出最近目录而关闭对话。
磁盘恢复不把旧运行标记当作实时状态，首次成功同步后再使用经过确认的目录状态。

验证入口：`tests/session-directory.test.mjs`、`mobile/test/state/session_directory_test.dart`、
`mobile/test/state/app_controller_project_cache_test.dart` 和 `mobile/test/ui/project_list_test.dart`。

## 2026-09-20 前台恢复优化验证

回前台立即读取 Desktop 内存目录，同时恢复实时通知并请求 bootstrap。保留本地缓存恢复、
单个在途目录请求、每批 50 条及后续每秒一批的限制，不为加速首页一次拉满 300 条。
bootstrap 完成或失败均不重启目录轮询，避免丢弃并行收到的新目录；后台/设备切换仍按 epoch
和授权 scope 丢弃过期结果。测试覆盖后台三分钟后，在 bootstrap 尚未完成时发布最新目录，
以及 bootstrap 成功/失败时保留在途响应。相关 Flutter 目录、实时和历史测试 64 项通过；
Desktop 目录测试 7 项通过。

合成数据测量（非用户实际目录、非网络端到端耗时）：300 条会话，标题为约 20 字中文，
一个项目，包含模型及运行状态；首批 50 条 JSON 为 13,117 字节，单条标题变化 408 字节，
无变化 168 字节。10,000 次无变化内存读取平均约 0.39ms。数值均为加密前 UTF-8 JSON，
不包含 envelope、Base64、HTTP/TLS 开销，也不代表长路径、大标题或大量项目的上限。
项目列表变化时仍整份返回，手机接受最多 2,000 项，后续大项目库需单独关注。
32 个旧快照过期或 Desktop 重启会回退到分页重建；首批可直接显示，完整目录仍需后续批次。

### 后续调整：单批 300 条

用户确认提高批量后，新手机显式请求 `batch_size: 300`，Desktop 校验为 1–300 的整数；
手机响应校验同步放宽至 300，整个目录仍最多 300 条。无需等待六次定时请求完成首次同步或
快照过期后的重建。后续仍只发增量，不会每秒传满 300 条。不携带正文、附件或模型配置菜单。
旧手机默认 50 条，以避免其严格的响应大小校验拒绝新版 Desktop；新手机兼容旧 Desktop 的
50 条分页。上节 50 条测量和限制记录属于调整前基线。

相同合成样本调整后，一批 300 条目录 JSON 为 76,557 字节；加入示例路由 AAD 的真实
A256GCM envelope JSON 为 102,606 字节（不含 HTTP/TLS）。本机 Node 连续 100 次加解密
往返平均约 1.15ms，不代表手机 CPU 或真实网络耗时。该样本首次同步从六批降至一批。
验证覆盖单批 300 条、增量、旧客户端默认 50 条、旧游标接续、非法批量拒绝与手机总量上限。


## 2026-09-21 命令到达即返回

Relay 与 Server 协商 `command_wait_ms: 20000` 后，通过原有
`GET /api/relay/commands?wait_ms=20000` 保持一个待返回请求。Server 先注册唤醒再查
持久化队列，空队列才等待；`POST /api/commands` 入库成功后唤醒目标设备，原请求重新
验证设备授权、取得租约并返回加密命令。Relay 收到响应立即续接，没有 750ms 定时空档。
首次启动仍立即查询，不用等首条命令才完成启动。旧服务器未声明能力时保留 750ms 轮询。

单个 Node 进程按设备保留一个等待，后来的连接替换旧等待；旧连接收到退避提示，避免
两个相同身份的 Relay 空转。客户端断开、Relay 退出或服务端停服均释放等待。20 秒超时
会重新查询持久队列，兼顾租约重取和授权快照刷新；网络故障仍按现有退避重连。
唤醒只传递进程内提示，不传会话数据、不替代租约或持久化。此实现面向当前单 Node
服务实例；未来横向扩容必须先增加跨实例唤醒，否则落到另一实例的命令只能超时后发现。

这只去掉命令获取的定时等待，网络往返、目录新鲜度、上传队列和手机响应获取仍需分别
测量。空闲命令 GET 的日志耗时接近 20 秒是主动等待，不代表命令传输耗时。需要同时更新
Server 和 Relay 才生效，单独安装新 Relay 连接旧服务器仍走兼容路径。

验证：命令长等待及相关加密、授权、附件、目录与启动回归共 80 项通过；TypeScript
检查和 self-hosted Server 打包通过。内存持久层测试中，从加密命令入库调用到待返回
请求完成约 2.15ms；该数值只验证取消固定等待，不包含真实 MongoDB、跨网传输或手机
界面耗时，不能用来宣称首页端到端延迟。Android 当时未连接，未做手机实测。

## 2026-09-21 会话状态与响应等待优化

周期刷新时，Relay 只等待 Agent 会话读取，然后立即发布目录；项目和用量独立刷新，
目录携带它们最近一次成功的缓存值。项目读取同样合并在途工作，慢查询不会每秒堆积。
项目和用量的新值在后续目录轮次发布。首次 Relay 注册仍读取完整目录；原生会话读取和
每秒刷新周期仍存在，此改动不宣称 Agent 状态已全面改为事件推送。

新 Server 在 bootstrap 声明 `response_wait_ms: 10000`。手机随后在原有
`GET /api/responses/:request_id` 携带 `device_id` 和 `wait_ms`，未就绪时保持该请求；
Relay 上传响应并完成持久化后，服务器立即唤醒对应授权、请求编号的等待并返回原密文，
无需等待 WebSocket 通知后再发一次 GET。结果早已存在时直接返回。

等待先验证账户、设备归属和客户端授权，先注册再读取以避免并发遗漏；唤醒或超时后
重新检查设备与客户端授权。等待只保存进程内提示，载荷仍在原有 MongoDB/私有 blob。
每个授权最多 8 个等待，单服务进程最多 2048 个；断开和停服释放等待，达到上限时退回
原 pending 响应。10 秒正常超时后手机立即续接，旧服务器及普通 pending 继续保留原有
通知唤醒和一秒重查。响应等待能力绑定 bootstrap 时的会话、客户端授权及设备，凭据
变化后不沿用旧作用域。现有 WebRTC 直连保持原路径。

服务器、Relay、手机需要分别更新对应部分；没有部署 Server 时不会启用响应长等待。
这些变化减少人为等待，不等于已测得 Android 首页的真实总耗时。


验证：相关 Node 测试 89 项、手机网络/历史/目录测试 49 项通过；类型检查、Flutter
静态检查、测试映射和 Server 打包通过。额外执行会话创建回归时有 4 项失败，使用改动前
`181043b` 的手机生产代码复测仍是同样 4 项：partial catalog 场景超时，以及 named
creation、explicit project creation、authoritative creation result 三项断言失败。
这些已有失败没有通过修改断言隐藏，也不计入本次通过数。Android 无 ADB 连接，未报告
真实手机端到端耗时或声称已消除所有 3–5 秒延迟。
