# macOS 自动性能日志

macOS Desktop 启动后自动采集本机诊断，不需要打开终端或手动开启开关。数据只写入本机，
不上传 Server，不占用 MongoDB，不包含会话正文、设备/会话标识、文件路径、URL、邮箱、
凭据或原始错误。进程 PID、Relay 启动代次、软件版本和时间用于关联同一次运行。

## 文件与保留

目录：`~/Library/Logs/cn.giraffetree.agent-relay/`。

- `performance.jsonl`：当前性能日志，每行一个 JSON 对象。
- `performance.1.jsonl` 至 `performance.4.jsonl`：从新到旧的滚动归档。
- `relay-lifecycle.jsonl`：已有的进程启动、连接、停止、意外退出及固定错误分类。

性能文件每份不超过 2 MiB，当前与归档合计最多 10 MiB。最长保留 7 天，大小达到上限会
更早滚动淘汰；应用不运行时不做后台清理，下次启动恢复清理。文件仅本机用户可读写
（0600）。性能日志的保留和大小上限不包含独立的生命周期日志。

## 采集内容

| 事件 | 内容 | 频率 |
| --- | --- | --- |
| `process_sample` | Rust Desktop 与当前 Relay 的 RSS、CPU，以及 Relay 连接状态 | 每 15 秒 |
| `relay_sample` | Relay RSS、JS heap used/total、external 内存、CPU、事件循环延迟、运行时长与实际采样间隔 | 每 15 秒及正常关闭时 |
| `startup_phase` | 本机状态准备、Agent 初始化、注册、首次同步、轮询、Hook 和构造准备各阶段耗时及成功/失败 | 阶段完成时 |
| `operation_timing` | 固定类别操作的次数、失败次数、总耗时、最大耗时 | 每 15 秒聚合 |
| `connection_timing` | 启动至连接、断开至恢复连接的总耗时 | 连接成功时 |

操作类别包括历史读取、会话目录读取与远端 HTTP 请求。本次整合不启用后台历史预热；历史读取计时覆盖实际 Agent 读取。目录计时覆盖读取会话列表，远端请求计时到收到响应头，不代表
响应正文全部下载完毕。长轮询正常等待也计入 HTTP 耗时，因此不能仅凭它持续数秒判断故障。

RSS 是这两个进程各自的驻留内存，不是整台机器或所有 WebKit/Agent 子进程的总内存。
JS heap/external 是 Relay 进程内的不同口径，不应直接与 RSS 相加。`process_sample` 的
CPU 来自系统 `ps`，`relay_sample` CPU 来自采样区间的进程 CPU 时间增量；100% 约代表
一个 CPU 核心，二者的统计窗口不同。

事件循环延迟是 1 秒定时器的最大迟到量。休眠、系统繁忙或 JS 阻塞都可能使它增大，
不是单个函数耗时。原生采样由独立线程执行，Relay 的 JS 卡住时仍会采样；若原生记录
持续出现而 Relay 自报样本中断，应结合生命周期和系统休眠情况排查。

## 开销与故障边界

原生采样只查询 Desktop 及它当前持有的 Relay PID，校验父进程与启动代次，不扫描其他
应用的命令行。系统采样有 2 秒截止。日志写入走有界队列，子事件限速，原始子进程输出
必须通过固定字段/枚举/数值校验才会保存。队列满、采样失败或磁盘无法写入不会阻塞业务；
部分样本可能缺失，不能把缺失值当成零。

程序退出后不继续监控。强制结束、系统崩溃或断电可能丢失最后尚未落盘的记录；这不是
崩溃转储或永久审计系统。异常退出后，可按时间、`desktop_pid`、`relay_pid` 和
`generation` 关联两类日志，查看退出前资源趋势及最后完成的启动阶段。
